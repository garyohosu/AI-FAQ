## 2. 現在の問題

現状は次の動作まで実装されている。

```text
質問者が質問
  ↓
AI・承認済み知識・取り込み資料で回答不能
  ↓
PENDING_HUMANを作成
  ↓
IT管理者が pending answer を実行
  ↓
回答を承認済み知識として保存
  ↓
終了
```

この状態では、IT管理者の回答が元の質問者へ自動的に紐付かない。

質問者は同じ質問を再度送れば新しい承認済み知識から回答できるが、これはヘルプデスクとして不自然である。

今回、次の形へ完成させる。

```text
質問者が質問
  ↓
人間回答待ち（受付番号・thread_id発行）
  ↓
IT管理者が別ターミナルで回答
  ↓
元のpendingとthreadへ人間回答を保存
  ↓
質問者が status または watch で受領
  ↓
同じ回答を承認済み知識として次回再利用
```

## 3. 想定する2ターミナル運用

同じリポジトリフォルダを、2つのターミナルで開く。

```text
ターミナルA: 質問者
ターミナルB: IT管理者
```

両方が同じ `data/aifaq.db` を参照する。

### 3.1 ターミナルA（質問者）

```bash
aifaq ask "第2工場のPC交換申請先は？" --thread-id demo-001 --requester 山田
```

人間引き継ぎとなった場合、最低限次を表示する。

```text
IT管理者へ引き継ぎました。
受付番号: 12
thread_id: demo-001
状態: 回答待ち

後から次のコマンドで確認できます:
aifaq status demo-001

回答を待ち続ける場合:
aifaq watch demo-001
```

### 3.2 ターミナルB（IT管理者）

```bash
aifaq pending list
aifaq pending show 12
```

人間が回答する。

```bash
echo "PC交換申請は情報システム部へ提出してください。" |
  aifaq pending answer 12 \
    --approved-by hantani \
    --category procedure \
    --tags pc,申請 \
    --reason "初回回答として承認"
```

### 3.3 ターミナルAで回答取得

一度だけ確認する場合:

```bash
aifaq status demo-001
```

回答待ちなら:

```text
[回答待ち]
受付番号: 12
thread_id: demo-001
質問: 第2工場のPC交換申請先は？
受付日時: ...
```

回答済みなら:

```text
[IT管理者からの回答]
PC交換申請は情報システム部へ提出してください。

受付番号: 12
thread_id: demo-001
回答者: hantani
回答日時: ...
```

継続して待つ場合:

```bash
aifaq watch demo-001
```

IT管理者が回答したら、質問者側へ表示して正常終了する。

## 4. 必須CLIコマンド

### 4.1 `aifaq status`

次のどちらでも検索できるようにする。

```bash
aifaq status THREAD_ID
aifaq status --pending-id 12
```

少なくとも次の状態を扱う。

- `NEEDS_CLARIFICATION`
- `PENDING_HUMAN` / `OPEN`
- `ANSWERED`
- `CANCELLED`
- `COMPLETED`
- 対象なし

出力には次を含める。

- thread_id
- pending ID（存在する場合）
- 元の質問
- 状態
- 確認質問履歴の要約
- AI回答または人間回答
- 回答者
- 受付日時
- 回答日時
- 回答種別
- 出典（ある場合）

`aifaq --json status ...` にも対応する。

### 4.2 `aifaq watch`

```bash
aifaq watch THREAD_ID
aifaq watch --pending-id 12
```

要件:

- 既定では2秒程度の間隔でSQLiteをポーリングする
- `--interval SECONDS` で変更可能
- 最短間隔は0.5秒以上に制限する
- `--timeout SECONDS` を指定可能
- 回答済みになったら回答を表示して終了コード0
- タイムアウト時は状態を表示して終了コード3など、READMEに定義した値を返す
- Ctrl+Cで安全に終了する
- 待機中に毎回大量の表示を行わない
- 状態が変わった場合だけ表示するか、簡潔な待機表示にする
- `--json`の場合は最終結果だけをJSON出力し、進捗表示でJSONを壊さない

### 4.3 `aifaq pending answer` の拡張

現行の承認済み知識保存は維持する。

それに加えて次を実施する。

1. pendingへ人間回答本文を保存
2. `answered_by` を保存
3. `answered_at` を保存
4. pending状態を `ANSWERED` へ変更
5. 元のthread_idへ人間回答結果を紐付ける
6. `query_history` または専用の回答履歴へ記録する
7. LangGraphのチェックポイントを、可能なら人間回答を受け取った完了状態へ進める
8. LangGraph再開が現在の設計上不自然・危険な場合は、業務状態をSQLite側で正としてstatus/watchから回答を返す。ただし理由を設計記録へ残す
9. 同じpendingへ二重回答しない
10. 二重実行時は既存回答を上書きせず、明確なエラーにする

### 4.4 `aifaq chat`（推奨、時間不足なら制約付き実装可）

CLIで確認質問を繰り返す対話モードを追加する。

```bash
aifaq chat --requester 山田
```

想定例:

```text
AI-FAQ CLI
終了: /quit
状態確認: /status

あなた> 社内Wi-Fiにつながりません
AI-FAQ> 他の端末は接続できますか？
  1. 自分の端末だけ
  2. 複数の端末
  3. 分からない
あなた> 1
AI-FAQ> IT管理者へ引き継ぎました。受付番号は12です。
AI-FAQ> このまま回答を待ちますか？ [Y/n]
```

要件:

- 既存の `run_ask` / `run_reply` を再利用する
- 独自にFAQロジックを重複実装しない
- 確認質問の最大3回制限を維持する
- パスワード等の秘密情報を入力させる誘導をしない
- `/status` で現在のthread状態を表示できる
- `/quit` で安全に終了する
- 人間回答待ちでは、待機するか終了するか選択できる

`chat`が今回完成しない場合でも、`status`、`watch`、人間回答の元threadへの保存は必須である。

## 6. 2ターミナル同時利用とSQLite対策

今回の実利用では、同じSQLite DBへ別プロセスからアクセスする。

次を確認・実装する。

- SQLiteのWALモードを検討し、適切なら初期化時に `PRAGMA journal_mode=WAL` を設定する
- `PRAGMA busy_timeout` を設定する
- 接続ごとに必要なPRAGMAが反映されること
- 短時間のロック競合を適切に再試行する
- 無限再試行しない
- 失敗時は「database is locked」の生メッセージだけでなく、利用者向けの説明を出す
- 質問者の `watch` がDBを長時間ロックしない
- ポーリングのたびに短い読み取りトランザクションで接続またはクエリを完了する
- `pending answer` 中でも別ターミナルの `status` が復旧可能であること

## 7. 状態遷移

最低限、次の状態遷移を明示する。

```text
OPEN / PENDING_HUMAN
  ├─ IT管理者が回答 → ANSWERED
  ├─ 管理者が取消 → CANCELLED
  └─ 未回答 → OPENのまま

ANSWERED
  ├─ 質問者がstatusで取得 → ANSWERED（取得だけでは状態を壊さない）
  └─ delivery記録を持つ場合 → delivered_atのみ更新
```

回答の「保存」と「質問者が読んだこと」は分離する。

回答を一度表示しただけで削除しない。

## 8. セキュリティ要件

- 機密質問をAntigravityへ送らない現行ルールを維持する
- 人間回答は外部AIへ送らない
- `watch` / `status`が別threadの情報を誤表示しない
- thread_idまたはpending IDの入力をSQL文字列へ直接連結しない
- JSON出力へ秘密情報を追加で漏らさない
- 人間回答の標準入力に含まれる制御文字・極端な長文を検証する
- 回答本文の上限を設定し、超過時は明示エラーにする
- 既存の伏字化ポリシーと整合させる

認証機能は今回のCLI MVP対象外だが、READMEに次を明記する。

- 同じPC・同じOSユーザーまたは信頼された管理環境での利用を想定
- DBファイルを読める利用者は質問・回答履歴を参照できる
- 複数社員へ配布する本番利用前には認証付きWeb UIまたは別のアクセス制御が必要
